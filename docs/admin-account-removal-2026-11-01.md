# Targeted removal in the ADMIN account directories

Super Admin can remove a cleaning company or a private/business client using **Șterge** in `/admin/firme` and `/admin/clienti`. The dialog identifies the exact target, requires its current name and a reason, and explains that account access is closed while historical jobs, evidence and financial records remain retained. Other staff roles do not receive this control and the API independently refuses them.

This is logical account removal, not a GDPR erasure executor or a global data reset. It does not delete the underlying user, firm, job, payment, document or external payment-provider account. The owner can therefore remove a test account without deleting other accounts or rewriting historical work. Romania pricing, foreign pricing drafts, Marketing and native packages are not changed.

`POST /api/admin/account-removal` requires an existing Super Admin session, a trusted admin origin, an exact kind/ID/name match and a bounded JSON payload. Active work, active recurrence, unsettled authorization/refund/dispute/transfer work and in-flight notification dispatch block removal. The server uses an immediate transaction, creates its own immutable removal marker lazily, revokes the selected account's sessions/devices, suppresses its pending notifications, stops its availability/ical/home-maintenance automation and records the authenticated actor in audit. Audit failure rolls all changes back. Replays do not duplicate the marker or audit entry.

Removed accounts are filtered out of the current firm/customer directories, core user/firm lookups, public provider lists/reviews and favorites. New sessions cannot be issued to a removed account. An old cookie or native bearer session no longer resolves to a user. Historical registration events and financial/work ledgers remain historical evidence.

Compatible read predicates tolerate databases predating the first removal and do not create schema on GET. The additive table is created only during a successful explicit removal. No anonymous endpoint, startup cleanup or broad delete exists. A type-only dashboard GET overload also satisfies Next 16 route generation without changing the handler's behavior.

Validation uses a production build in a network-isolated container with synthetic company/client/admin accounts. No production account or real notification/payment is used. Unit/API regression checks cover authorization, origin, confirmation, exact targeting, preserved history, financial/active-work guards, audit rollback, retry idempotency and legacy-database reads. Browser checks exercise both directory controls, cancel/mismatched confirmation, successful removal, active-work refusal, cookie revocation and rejected subsequent login on desktop/mobile widths.

Release this independently of international price PR #176. Existing firms are not automatically removed by deploying this code: an authorized administrator must explicitly confirm each row. After removal markers exist, keep the account-status guards in any rollback/forward fix; an older version unaware of markers cannot enforce this account lifecycle. An operator must not drop the marker table or rewrite existing historical records as a rollback shortcut.
